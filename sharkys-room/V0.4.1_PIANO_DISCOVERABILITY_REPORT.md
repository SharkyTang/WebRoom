# Sharky's Room — v0.4.1 Piano Discoverability Fix

验收日期：2026-09-17。基于已验收的 v0.4，仅修改 Web 交互层。

**SHARKY'S ROOM --- v0.4.1 PIANO DISCOVERABILITY FIX COMPLETE**

## 1. 根因

钢琴收回到桌下后，原有可见网格被桌体遮挡；R3F 的正常遮挡／最近命中规则使该区域无法自然选中钢琴。v0.4 的 Explore objects 可以绕过可见性，但用户必须预先知道选择器。模型、轨道和相机端点本身没有错误。

## 2. 实现架构与语义映射

- `components/room/PianoRetractedHitArea.tsx` 创建单个 Web 专用 box mesh，作为冻结模型的运行时兄弟节点。
- `RoomModel` 的同一个事件 group 包含冻结模型与代理；沿用 `useRoomInteractions → resolveInteraction → store.activate('piano')`，不另建点击或动画系统。
- `interactiveObjects.ts` 新增独立的 `runtimeInteractionTargets` 注册表，将 `PianoRetractedHitArea` 映射为 `piano`。它不进入 `requiredNodeNames`，也不是 GLB 契约的一部分。
- `pianoInteraction.ts` 集中定义区域尺寸和启用条件。不会把整个桌子映射为钢琴；普通桌面、椅子和其他语义节点继续使用原有命中规则。
- 仅为支持聚焦后再次悬停，状态仓库允许 `focused` 时悬停当前物件，保持 `focused` 阶段不变；其他物件不能通过此路径抢走焦点。

## 3. 点击区位置、大小和遮挡

坐标使用加载后的 glTF Y-up 世界坐标，单位为米。没有 Blender 轴转换或对模型做任何变换。

| 参数 | 数值 |
| --- | --- |
| 中心 `[x, y, z]` | `[-0.65, 0.52, -1.35]` |
| 宽 × 高 × 深 | `1.50 × 0.32 × 0.40` |
| x 范围 | `[-1.40, 0.10]` |
| y 范围 | `[0.36, 0.68]` |
| z 范围 | `[-1.55, -1.15]` |

区域覆盖桌前下方的抽拉位置，顶部低于约 `0.74m` 的桌面，未延伸到椅子前方。最近表面命中规则保持不变，没有提高代理的射线优先级或穿透前方物件。桌下结构属于预期的钢琴发现区域，正常桌面保持非交互。

390×844 视口使用原有 360×240 的 3:2 房间画布：实测可命中区域外接范围约 **43×25 CSS px**，含 **601 个可用整数像素**；区域受透视和遮挡影响，并非完整矩形。

## 4. 启用／停用规则

必须同时满足：场景已 ready、`pianoState === 'retracted'`、相机空闲、没有排队返回；并且处于 Hero 的 idle／hovering，或当前 Piano 的 focused 状态。

下列情况完全卸载代理网格：extended、extending、retracting、相机 focusing／returning、机构 interacting、排队 Back、其他物件处于焦点。收回完成并到达精确端点之后才启用，首次聚焦时的“先收再抽”中间阶段也不会启用。连续点击仍由原有状态机互斥处理。

## 5. 桌面行为

Hero 或 Piano 聚焦视角下，悬停已启用的区域使用 pointer 光标，页脚现有提示显示 **Pull-out Piano**，沿用原有轻微模型高亮。点击通过同一 `piano` 语义重新抽出。代理本身永远不会因悬停显形。

钢琴展开后只使用原有真实网格，悬停提示 **Put away Piano**。Explore objects、面板 Toggle piano、Back／Esc 全部保留。

## 6. 触屏行为

390×844 浏览器触屏模拟中，先收回并返回 Hero，再直接 tap 桌下区域即可重新聚焦并抽出，无需 hover 或选择器。测试三个不同整数坐标，连续三轮成功；Back 可见且触控尺寸至少 40×40，返回精确 Hero。桌面、椅子和地板的负例 tap 未打开钢琴。

## 7. 机构与相机保持不变

没有修改 `mechanisms.ts`、`animationConstants.ts`、`focusViews.ts`、相机控制器或冻结资产。

| 检查项 | 保留值 |
| --- | --- |
| `INT_PianoRail.position.z` 收回端点 | `-1.9399999618530273` |
| 抽出端点 | `-1.2899999618530273` |
| travel | `+0.65m` |
| 焦点 | 原有 `TGT_Piano` 与焦点偏移 |
| 返回 | 精确 `CAM_Hero_FINAL` position / quaternion / projection |

端点采用原有绝对赋值，没有增量累加。四轮桌面 rediscovery 测试逐次验证完整 position 和 Hero camera，对动画过程抽样检查代理不会提前启用。原有反复 Toggle、竞争点击和 Back 排队测试继续保留。

## 8. 调试和性能

- `?debug=1`：保留原有开发面板和只读 API，新增 `pianoRetractedHitAreaActive`，同时显示 `pianoState`。
- `?debug=1&hitareas=1`：仅开发环境显示活动区域线框；非活动时没有线框。
- `?debug=1&demand=1`：使用按需渲染测量动画后停止绘帧。
- `projected()` 按当前运行时场景取可命中像素；`hitTest(x,y)` 只读返回最近对象、祖先、语义和 runtime target。这些辅助函数仅在主动请求时 raycast。
- 正常模式材质 `visible=false`，无颜色或深度写入、无额外绘制调用；12 个三角面的简单 box 只参与事件驱动的射线检测。停用后不参与射线检测。
- 没有增加逐帧 raycast、第二个动画循环、后期处理或常驻热点。原有普通模式 `frameloop="demand"` 保留。
- 生产忽略 `debug` / `hitareas`，无开发面板、全局调试 API 或线框。

## 9. 新增测试

`tests/piano-discoverability.test.ts` 新增 6 项：四种机构状态与交互阶段／焦点／忙碌组合，独立 runtime 语义契约，以及真实 GLB 下 360×240 整数射线扫描，检查可用触控范围和正常桌面／椅子／其他语义物件不被代理覆盖。

`tests/piano-discoverability-browser.mjs` 使用真实浏览器输入，诊断仅观察，不直接调用控制器修改状态。覆盖：真实展开网格、聚焦内重开、四轮 Hero 重开、重复点击、精确端点和相机、负例、选择器后备入口、排队 Back、按需渲染、开发线框、触屏三坐标、reduced motion、正常隐藏模式及生产无诊断重开。

原有三个浏览器脚本仅增加可选 `ROOM_TEST_OUTPUT`，断言保留，避免覆盖 v0.4 历史证据。
